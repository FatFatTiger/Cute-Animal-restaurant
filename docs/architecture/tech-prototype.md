> 可爱小动物「卡牌收集 + 餐厅放置经营」治愈系微信小游戏 · 技术原型规格
> 版本：v0.1 · 状态：草稿（验证逻辑层已实跑，构建/真机项待证伪） · 作者：engineering-lead

> **修订：2026-07-29 pivot to canvas2d（用户 OP1-A）**：引擎由「Cocos Creator + 微信引擎插件」改为「微信原生 canvas2d（`wx.createCanvas().getContext('2d')`，无 Cocos）」；删除 Spine / ASTC / WebGL shader tint 表述，保真靠程序化图元 + 分层 fill。不变量 #1（零位图 / 贴图零增长）、#2（家族硬隔离）保持不变。美术资产附录冲突见 `system-scene-map.md` §0.1 / OP1。

## 1. 概述与目标

本规格定义一个 **4MB 主包** 约束下的微信小游戏技术原型。核心目标是**证明主包资产风险在架构层面已被消解**：即无论动物图鉴规模如何扩张，单只动物的新增资源成本趋近于零，主包永远不会因"加动物"而爆包。

原型证明的三件事：

1. **资产零增长**：所有可换装的"白模"部件集中在一张基础部件图集（base-parts atlas）中，加入新动物 = 仅写入一份 ~11B 的 JSON 参数，不新增任何独立贴图字节。
2. **家族硬隔离**：跨家族的部件组合在运行时被强制拒绝（`FamilyIsolationError`），保证拼装结果始终符合美术与设定逻辑。
3. **分层上色**：身份色（角色填充）与稀有度色（UI 卡框）属于不同 UI 层，由 canvas2d 分层 fill（不同 fill 参数）实现，互不干扰（修订：2026-07-29 pivot to canvas2d，原「着色器 tint」改为程序化分层上色）。

**范围边界**：本原型为*逻辑层验证*，已通过 Node 实跑论证上述 1–3。涉及微信原生 canvas2d 渲染管线、真机性能与计费链路的项目（V4–V7、R1–R7）**尚未**在真实构建/真机中验证，统一标记为"待证伪"，见第 7、8 节。

**已锁定决策（不可重开）**：平台=微信小游戏、引擎=微信原生 canvas2d（无 Cocos / 引擎插件，pivot 2026-07-29）、资产策略=程序化图元绘制（零位图）、家族硬隔离、分层 fill 上色、稀有度 N/R/SR/SSR、抽卡池 R60/SR30/SSR10 + 50 抽保底。

## 2. 五层架构

| 层 | 名称 | 职责 | 技术选型 |
|----|------|------|----------|
| **L1** | 平台/运行时层 | 微信小游戏运行时容器、生命周期、分包加载 | 微信小游戏运行时 + 微信原生 canvas2d（`wx.createCanvas().getContext('2d')`，无 Cocos / 引擎插件，**不计入 4MB 主包**） |
| **L2** | 核心引擎服务层 | 渲染、音频、输入、本地存档（`wx.getStorage`）、网络与登录 | 微信原生 canvas2d 渲染 + `wx.*` API 封装（存档、分享、登录态） |
| **L3** | 资产管线层 | 程序化拼装：基础部件绘制函数库 + 动物参数 + 分层 fill 上色（零位图） | 程序化部件绘制函数库（canvas2d 矢量原语）+ JSON 参数注册表 + 分层 fill（pivot 2026-07-29：原「Shader tint」改为程序化分层上色） |
| **L4** | 玩法系统层 | 抽卡（gacha）、餐厅放置经营、动物养成 | 纯逻辑模块：抽卡概率与 50 抽保底、经营产出循环、养成数值；数据驱动，不依赖热路径分配 |
| **L5** | 元游戏与 UI 层 | 主菜单 / 抽卡界面 / 餐厅 / 图鉴 / 商店；IAP+IAA、广告、可选云存档 | 微信原生 canvas2d UI（绘制指令树，不持有游戏状态）+ 微信支付/广告 SDK + 可选云存档同步 |

**数据与联网（贯穿 L4/L5）**：抽卡与经营为本地权威（单机可玩）；IAP 支付、激励视频广告（IAA）、可选云存档为服务端/微信侧权威，需真机接入与计费链路验证（见 R5/R6）。

## 3. 架构决策记录（ADR）

### ADR-1 引擎选型：微信原生 canvas2d（无 Cocos / 引擎插件）
- **状态**：已接受（LOCKED）
- **修订**：2026-07-29 pivot to canvas2d（用户 OP1-A）。原 ADR-1（Cocos Creator + 微信引擎插件）作废，本 ADR 取代之。
- **背景**：微信小游戏主包硬上限 4MB，传统"引擎打进主包"会直接吃掉 1–3MB，挤压内容空间；且 Cocos 引擎插件依赖微信端引擎版本一致性。E7 真机已用微信原生 `wx.createCanvas().getContext('2d')` 跑通渲染循环，证实可行。
- **决策**：采用**微信原生 canvas2d**（纯 `wx.createCanvas()` + `getContext('2d')`，零引擎 / 零 Cocos），所有视觉为运行时程序化图元绘制；引擎运行时由微信客户端在端上提供，**不占用开发者主包体积**。
- **影响**：主包从立项起即释放引擎体积，主包只含 JS + 字体子集（零位图）；与既有 E7 实装一致。代价是渲染需用 canvas2d 图元手写（圆角/椭圆/渐变/路径），已由 `src/ui/render.js` 的工程化绘制库承担。
- **备选**：(a) Cocos Creator + 微信引擎插件——原方案，因 pivot 离 Cocos 作废；(b) 自研轻量引擎——可控但开发与维护成本过高；(c) Unity 小游戏适配——体积与启动成本不适合 4MB 约束。均否决。

### ADR-2 程序化拼装资产管线（绘制函数库 + 参数，零位图，单只 0 独立贴图）
- **状态**：已接受（LOCKED）
- **修订**：2026-07-29 pivot to canvas2d。删除 Spine / ASTC / WebGL shader tint 表述；"base-parts atlas" 在零位图范式下 = **一套程序化部件绘制函数库**（canvas2d 矢量原语 + JSON 参数）。不变量 #1（贴图零增长 → 零位图成立）、#2（家族硬隔离）保持不变。
- **背景**：治愈系动物需大量可换装变体（头/身/耳/尾/肢 + 表情/配饰/配色）。若每只动物独立美术，图鉴规模与贴图体积线性爆炸，4MB 主包不可持续。
- **决策**：所有可换装部件收敛到**一套程序化绘制函数库**（`drawCatHead` / `drawBirdBody` 等）+ JSON 参数注册表（head×6 / body×5 / ear×8 / tail×6 / limb×3 + face / accessory）。加入新动物 = 仅写入一份 ~11B 的 JSON 参数，零新增贴图字节（不变量 #1）。
- **影响**：图鉴规模与包体解耦，运营可持续扩量；拼装顺序固定（body→head→ear/tail→face→accessory）。代价是美术须按"白模 + 槽位"范式生产，配色靠 12 套预设（COLOR_PRESETS）参数化；分层上色由 canvas2d 分层 fill 实现（见 ADR-4），无 shader tint。
- **备选**：(a) 每动物独立精灵图——体积爆炸；(b) Spine 骨骼动画逐动物——精度高但资产与运行成本双高，且依赖位图/骨骼资源，违反零位图；(c) LOD/合批预烘焙——仍随规模增长。均因违反 4MB / 零位图约束被否决。

### ADR-3 主包/分包切分策略（4MB 主包仅放引导+核心框架，内容进分包）
- **状态**：已接受（LOCKED）
- **背景**：4MB 只约束主包；微信支持分包（16MB+）按需加载。
- **决策**：主包只放**核心框架 JS（微信原生 canvas2d）+ 引导程序化绘制库参数（零位图）+ 引导配置 JSON + 字体**；餐厅场景、扩展图鉴、音频音乐、活动运营等全部进分包，按需下载。
- **影响**：首屏可控制在约 1.3–1.9MB（见第 4 节），留足缓冲；分包命中需构建与真机验证（V7/R4）。代价是首启分包时有下载/解压等待，需 Loading 与缓存策略。
- **备选**：(a) 全量打进主包——直接爆 4MB；(b) 主包塞满 3.9MB 内容——牺牲引导体验与后续扩展余量。均否决。

### ADR-4 分层上色（身份色 vs 稀有度色分属不同 UI 层，canvas2d 分层 fill）
- **状态**：已接受（LOCKED）
- **修订**：2026-07-29 pivot to canvas2d。原「顶点色 / Shader tint 分层」改为「canvas2d 分层 fill（不同 fill 参数）」，删 shader tint 表述。
- **背景**：同一动物在图鉴、抽卡、餐厅、卡牌中既要保留"角色身份配色"，又要叠加"稀有度框架配色"，二者语义不同、易互相污染。
- **决策**：采用**canvas2d 分层 fill**——身份色（character fill）作用于角色绘制层，稀有度色（N/R/SR/SSR 卡框）作用于 UI 卡牌框架层，二者分属不同绘制指令层，独立填充、互不覆盖。N=免费基础动物，不进抽卡池；抽卡池 R60/SR30/SSR10，50 抽保底。
- **影响**：角色视觉与稀有度视觉解耦，换皮/换稀有度无需改绘制函数；配色靠 12 套预设（COLOR_PRESETS）参数化。代价是分层 fill 在低色域/老旧设备上的还原一致性需真机验证（R3）。
- **备选**：(a) 稀有度单独出图——又回到"贴图随规模增长"；(b) 同层半透明叠加——视觉串色、难控。均否决。

## 4. 首包预算表

> 主包硬上限 **4MB**。以下为保守预算信封（单位 MB），合计 < 4MB，留足缓冲。

| 行 | 项目 | 体积 | 说明 |
|----|------|------|------|
| 1 | 引擎插件 | **0** | 无引擎插件；微信原生 canvas2d 由微信客户端提供，不计入主包 |
| 2 | 核心框架 JS | 0.3 – 0.5 | 微信原生 canvas2d 框架 + L2 服务封装 + L4 玩法逻辑 |
| 3 | 引导程序化绘制库参数 | ≈0 | 零位图：引导部件绘制函数 + JSON 参数（首屏引导所需槽位子集），无 atlas 字节 |
| 4 | 引导配置 JSON | ~0.02 | 引导流程/首屏动物参数（≈11B/只量级） |
| 5 | 字体 | 0.1 – 0.2 | 中文 UI 字体子集（建议按需裁剪/分包） |
| — | **合计** | **≈0.42 – 0.92** | 取保守上沿约 **0.4 – 0.9MB**（零位图后显著下降），缓冲 ~3.1 – 3.6MB |

> 注：参考实现 `assembly-demo.js` 中 `ATLAS_BYTES = 466096`（≈0.45MB）为白模 atlas 的代表性子集常量；pivot 2026-07-29 后「atlas」映射为**程序化参数注册表**（零位图，新增动物 ≈11B/只），该常量仅作逻辑层零增长论证参考，真实首包尺寸以 `tests/smoke/build-size.gate.js` 构建近似实测值为准（见第 7 节 V4 与风险 R-ATLAS-CONST）。

## 附录：已标记风险（engineering-lead 注）

- **R-LOGIC（主风险）**：`assembly-demo.js` 为**纯逻辑 Node 证明**，未实例化引擎插件、着色器或 `wx.*` API。它验证了*资产规模策略*（程序化参数零增长 + 紧凑参数 + 家族守卫）；pivot 2026-07-29 后「atlas」= 程序化参数注册表（零位图）。但 **4MB 主包声明尚未被真实构建构造性证明**——属于"资产层逻辑消解"，须由真实构建 + 微信开发者工具真机运行补足（V4–V7、R1–R7）。
- **R-ATLAS-CONST**：`ATLAS_BYTES = 466096` 为硬编码占位常量；零增长断言对该值不敏感，但**绝对基线须以真实构建产物实测值替换**（零位图，参数注册表），并复核第 4 节预算行（pivot 后 ≈0.4–0.9MB）。
- **R-GUARD-NUANCE**：家族守卫仅在"槽位声明家族集不包含动物家族"时抛错；`universal` 与显式多家族槽位（limb `L0=[mammal,bird]`、`L2=[round,aquatic]`）属**白名单例外**，须作为设计意图保留，勿误读为"任意跨家族皆错"。
- **R-ENCODE**：`packAnimal()` 对 `deform` 字段做 8 位截断（`& 0xFF`）。`headBodyRatio*10` 与 `scale*100` 在 guide 区间内（scale≈1.0、ratio≈2.5）安全；正式实现须在打包前**钳制/校验**，避免超界静默回绕（wrap）。
- **R-GACHA-OUT-OF-SCOPE**：50 抽保底、R60/SR30/SSR10 抽卡池与 N 不入池为设计锁定项，本 demo 未实现抽卡逻辑，需在 L4 玩法系统层补真实实现与单测。
