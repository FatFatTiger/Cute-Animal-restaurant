# 技术原型规格 v0.1 — 4MB 微信小游戏

> 可爱小动物「卡牌收集 + 餐厅放置经营」治愈系微信小游戏 · 技术原型规格
> 版本：v0.1 · 状态：草稿（验证逻辑层已实跑，构建/真机项待证伪） · 作者：engineering-lead

---

## 1. 概述与目标

本规格定义一个 **4MB 主包** 约束下的微信小游戏技术原型。核心目标是**证明主包资产风险在架构层面已被消解**：即无论动物图鉴规模如何扩张，单只动物的新增资源成本趋近于零，主包永远不会因"加动物"而爆包。

原型证明的三件事：

1. **资产零增长**：所有可换装的"白模"部件集中在一张基础部件图集（base-parts atlas）中，加入新动物 = 仅写入一份 ~11B 的 JSON 参数，不新增任何独立贴图字节。
2. **家族硬隔离**：跨家族的部件组合在运行时被强制拒绝（`FamilyIsolationError`），保证拼装结果始终符合美术与设定逻辑。
3. **分层上色**：身份色（角色填充）与稀有度色（UI 卡框）属于不同 UI 层，由着色器 tint 分层渲染，互不干扰。

**范围边界**：本原型为*逻辑层验证*，已通过 Node 实跑论证上述 1–3。涉及微信引擎插件、Cocos 渲染管线、WebGL 着色器、真机性能与计费链路的项目（V4–V7、R1–R7）**尚未**在真实构建/真机中验证，统一标记为"待证伪"，见第 7、8 节。

**已锁定决策（不可重开）**：平台=微信小游戏、引擎=Cocos Creator+微信引擎插件、资产策略=程序化拼装、家族硬隔离、白模 atlas+着色器 tint 分层上色、稀有度 N/R/SR/SSR、抽卡池 R60/SR30/SSR10 + 50 抽保底。

## 2. 五层架构

| 层 | 名称 | 职责 | 技术选型 |
|----|------|------|----------|
| **L1** | 平台/运行时层 | 微信小游戏运行时容器、生命周期、分包加载、引擎插件注入 | 微信小游戏运行时 + Cocos Creator 引擎插件（运行时由微信客户端提供，**不计入 4MB 主包**） |
| **L2** | 核心引擎服务层 | 渲染、音频、输入、本地存档（`wx.getStorage`）、网络与登录 | Cocos 渲染/音频/输入系统 + 微信 `wx.*` API 封装（存档、分享、登录态） |
| **L3** | 资产管线层 | 程序化拼装：白模基础部件图集 + 动物参数 + 着色器 tint 分层上色 | 单张 base-parts atlas（PNG/WebP）+ JSON 参数注册表 + 顶点色/Shader tint 着色器 |
| **L4** | 玩法系统层 | 抽卡（gacha）、餐厅放置经营、动物养成 | 纯逻辑模块：抽卡概率与 50 抽保底、经营产出循环、养成数值；数据驱动，不依赖热路径分配 |
| **L5** | 元游戏与 UI 层 | 主菜单 / 抽卡界面 / 餐厅 / 图鉴 / 商店；IAP+IAA、广告、可选云存档 | Cocos UI（cc.Node 树，不持有游戏状态）+ 微信支付/广告 SDK + 可选云存档同步 |

**数据与联网（贯穿 L4/L5）**：抽卡与经营为本地权威（单机可玩）；IAP 支付、激励视频广告（IAA）、可选云存档为服务端/微信侧权威，需真机接入与计费链路验证（见 R5/R6）。

## 3. 架构决策记录（ADR）

### ADR-1 引擎选型：Cocos Creator + 微信引擎插件
- **状态**：已接受（LOCKED）
- **背景**：微信小游戏主包硬上限 4MB，传统"引擎打进主包"会直接吃掉 1–3MB，挤压内容空间。
- **决策**：采用 Cocos Creator 开发，并启用**微信引擎插件**——引擎运行时由微信客户端在端上提供，不占用开发者主包体积。
- **影响**：主包从立项起即释放引擎体积；开发者仅需关注自身代码与资产。代价是构建须显式"引擎外置"，且依赖微信端引擎版本一致性（R2/R6 真机冷启动与版本兼容需证伪）。
- **备选**：(a) 自研轻量引擎——可控但开发与维护成本过高；(b) 纯原生 Canvas 手写——最省体积但重造轮子；(c) Unity 小游戏适配——体积与启动成本不适合 4MB 约束。均否决。

### ADR-2 程序化拼装资产管线（单 atlas + 参数，单只 0 独立贴图）
- **状态**：已接受（LOCKED）
- **背景**：治愈系动物需大量可换装变体（头/身/耳/尾/肢 + 表情/配饰/配色）。若每只动物独立美术，图鉴规模与贴图体积线性爆炸，4MB 主包不可持续。
- **决策**：所有可换装白模部件收敛到**一张基础部件图集**（head×6 / body×5 / ear×8 / tail×6 / limb×3 + face / accessory），运行时由一份 ~11B 的 JSON 参数拼装。加入新动物 = 零新增贴图字节。
- **影响**：图鉴规模与包体解耦，运营可持续扩量；拼装顺序固定（body→head→ear/tail→face→accessory，见 L3 z-order）。代价是美术必须按"白模 + 槽位"范式生产，且依赖着色器 tint 还原配色（R3 低色域表现待证伪）。
- **备选**：(a) 每动物独立精灵图——直观但体积爆炸；(b) 骨骼动画逐动物——精度高但资产与运行成本双高；(c) LOD/合批预烘焙——折中但仍随规模增长。均因违反 4MB 约束或运营灵活性被否决。

### ADR-3 主包/分包切分策略（4MB 主包仅放引导+核心框架，内容进分包）
- **状态**：已接受（LOCKED）
- **背景**：4MB 只约束主包；微信支持分包（16MB+）按需加载。
- **决策**：主包只放**引擎占位（0MB，外置）+ 核心框架 JS + 引导白模 atlas + 引导配置 JSON + 字体**；餐厅场景、扩展图鉴、音频音乐、活动运营等全部进分包，按需下载。
- **影响**：首屏可控制在约 1.3–1.9MB（见第 4 节），留足缓冲；分包命中需构建与真机验证（V7/R4）。代价是首启分包时有下载/解压等待，需 Loading 与缓存策略。
- **备选**：(a) 全量打进主包——直接爆 4MB；(b) 主包塞满 3.9MB 内容——牺牲引导体验与后续扩展余量。均否决。

### ADR-4 着色器 tint 分层上色（身份色 vs 稀有度色分属不同 UI 层）
- **状态**：已接受（LOCKED）
- **背景**：同一动物在图鉴、抽卡、餐厅、卡牌中既要保留"角色身份配色"，又要叠加"稀有度框架配色"，二者语义不同、易互相污染。
- **决策**：采用**顶点色/Shader tint 分层**——身份色（character fill）作用于角色模型层，稀有度色（N/R/SR/SSR 卡框）作用于 UI 卡牌框架层，二者分属不同 UI 层，独立渲染、互不覆盖。N=免费基础动物，不进抽卡池；抽卡池 R60/SR30/SSR10，50 抽保底。
- **影响**：角色视觉与稀有度视觉解耦，换皮/换稀有度无需改模型贴图；配色靠 12 套预设（COLOR_PRESETS）参数化。代价是 tint 在低色域/老旧设备上的还原一致性需真机验证（R3）。
- **备选**：(a) 稀有度单独出图——又回到"贴图随规模增长"；(b) 同层半透明叠加——视觉串色、难控。均否决。

## 4. 首包预算表

> 主包硬上限 **4MB**。以下为保守预算信封（单位 MB），合计 < 4MB，留足缓冲。

| 行 | 项目 | 体积 | 说明 |
|----|------|------|------|
| 1 | 引擎插件 | **0** | 由微信客户端提供，不计入主包 |
| 2 | 核心框架 JS | 0.3 – 0.5 | Cocos 业务框架 + L2 服务封装 + L4 玩法逻辑 |
| 3 | 引导白模 atlas | 0.8 – 1.2 | 基础部件图集（首屏引导所需槽位子集） |
| 4 | 引导配置 JSON | ~0.02 | 引导流程/首屏动物参数（≈11B/只量级） |
| 5 | 字体 | 0.1 – 0.2 | 中文 UI 字体子集（建议按需裁剪/分包） |
| — | **合计** | **≈1.22 – 1.92** | 取保守上沿约 **1.3 – 1.9MB**，缓冲 ~2.1 – 2.8MB |

> 注：参考实现 `assembly-demo.js` 中 `ATLAS_BYTES = 466096`（≈0.45MB）为白模 atlas 的代表性子集常量；真实首包白模 atlas 须以构建产物实测值替换（见第 7 节 V4 与风险 R-ATLAS-CONST）。

## 附录：已标记风险（engineering-lead 注）

- **R-LOGIC（主风险）**：`assembly-demo.js` 为**纯逻辑 Node 证明**，未实例化 Cocos 引擎插件、WebGL 着色器或 `wx.*` API。它验证了*资产规模策略*（atlas 零增长 + 紧凑参数 + 家族守卫），但 **4MB 主包声明尚未被真实构建构造性证明**——属于"资产层逻辑消解"，须由真实 Cocos 分包构建 + 微信开发者工具真机运行补足（V4–V7、R1–R7）。
- **R-ATLAS-CONST**：`ATLAS_BYTES = 466096` 为硬编码占位常量；零增长断言对该值不敏感，但**绝对基线须以真实烘焙图集实测值替换**并复核第 4 节 0.8–1.2MB 行（demo 当前 ≈0.45MB，舒适低于上沿）。
- **R-GUARD-NUANCE**：家族守卫仅在"槽位声明家族集不包含动物家族"时抛错；`universal` 与显式多家族槽位（limb `L0=[mammal,bird]`、`L2=[round,aquatic]`）属**白名单例外**，须作为设计意图保留，勿误读为"任意跨家族皆错"。
- **R-ENCODE**：`packAnimal()` 对 `deform` 字段做 8 位截断（`& 0xFF`）。`headBodyRatio*10` 与 `scale*100` 在 guide 区间内（scale≈1.0、ratio≈2.5）安全；正式实现须在打包前**钳制/校验**，避免超界静默回绕（wrap）。
- **R-GACHA-OUT-OF-SCOPE**：50 抽保底、R60/SR30/SSR10 抽卡池与 N 不入池为设计锁定项，本 demo 未实现抽卡逻辑，需在 L4 玩法系统层补真实实现与单测。
