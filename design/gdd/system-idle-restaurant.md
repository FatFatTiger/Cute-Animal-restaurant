## 1. 系统概述与目标

- **定位**：P2「经营」支柱核心；以放置 + 离线产出「被照顾」的治愈反馈，是 `星券`（软货币）**唯一生产源头**。
- **员工 / 顾客 二分（接手修订核心）**：
  - **员工（employee）** = 玩家拥有的动物（经抽卡 system-gacha / 养成 system-cultivation 获得），可上岗到 **厨师 / 服务员 / 接待** 三岗之一，是经营的生产者。
  - **顾客（customer）** = 系统生成的可爱动物访客，上门时携带一个「想吃的菜」需求；**该菜未解锁则无法被服务（不能结账、不产出）**，从而让「解锁菜品」成为经营核心驱动力。
- **Player Fantasy**：看着自己养的小动物员工把店开起来、服务一波波带菜需求的顾客，自己偶尔来「收菜」「解锁新菜」。
- **成功指标**：次留 / 7 留、日均在线收菜次数、离线收益领取率、星券产出满足升级 / 抽卡 / 菜品解锁三方消耗的自洽度、已解锁菜品覆盖率。
- **设计红线**：零失败无惩罚；节奏慢；单局 ≤5 分钟；「被照顾而非在打工」；顾客需求未解锁仅「暂缓服务」，绝不构成惩罚。

## 2. 核心机制

- **核心循环**：`顾客上门(带菜需求) → 员工三岗服务 → 结算(星券/食材) → 解锁菜品 / 升级扩张`。
- **员工三岗（role）**：玩家将拥有的动物分配到三岗，各岗提供不同生产加成（详见 §3.3）：
  - **厨师（chef）**：影响出餐价值 / 烹饪速度（作用于 `recipe_mult` 与 `T_cook`）。
  - **服务员（waiter）**：影响服务速度（缩短 `T_serve`，提升吞吐）。
  - **接待（host）**：影响顾客到店节奏与并发（缩短 `T_spawn`、提升有效座位 `C_eff` 与需求匹配）。
  - **岗位适配**：每只动物由家族/属性决定一个主适配岗（程序化拼装参数 `role_affinity`）；在适配岗上岗获得适配加成（见 §3.3），非适配岗仅基础加成。制造「哪只动物放哪个岗」的策略深度。
- **顾客生成（带需求）**：顾客按节奏到店（§3.4），占座后出示一个 `dish_demand`：
  - 若 `dish_demand ∈ 已解锁菜品` → 由在岗员工按 §3.1 公式结算，付星券 + 食材。
  - 若 `dish_demand ∉ 已解锁菜品` → **无法服务**，顾客等待（无惩罚），座位占用但零产出，UI 提示「解锁『XX』可服务」。这是驱动玩家解锁菜品的核心张力。
- **升级树三分支 + 菜品解锁（均消耗 `星券`，菜品解锁额外消耗 `食材`）**：
  - **座位（Seats）**：提升座位容量 `C`，提高顾客并发上限。
  - **工位（Stations）**：提升服务速度 / 单位产出倍率。
  - **菜谱（Recipes）**：提升订单基础价值 `V`。
  - **菜品解锁（Dish Unlock）**【新增 sink】：消耗 `星券 + 食材` 解锁新菜（详见 §3.5），解锁后方可被顾客点单。**不引入任何新资源**，食材本就是经营副产。
- **装饰 / 装扮**：纯表现或弱加成（详见装扮系统，本 GDD 仅预留槽位）。
- **状态机（经营）**：
  `开店 → 顾客生成(带菜需求) → 占座 → [菜已解锁?] → 员工三岗服务(被动结算+主动加成) → 结账产出(星券/食材) → 离线累积(下线) → 上线领取`

## 2.5 双流经济模型（2026-07-29 重大修订）

> ⚠️ 本节由主理人游承峰在 design-strategist agent 空回时按兜底纪律 dirext 增补，标注「**待 design-strategist 复核签字**」。经济方向（双流 + 餐厅为主、宿舍为辅、离线仅宿舍）经用户拍板锁定，数值为初稿 tunable。

此前的 Phase 3 把在线收益做成 100% 时间流（`idle.tick` 场景无关 `I_eff×dt`），与「餐厅为主、宿舍为辅」的设计意图相反。现正式将经济重构为**双流**：

| 流 | 性质 | 收入速率 | 在线占比目标 | 离线 |
|---|---|---|---|---|
| **A. 餐厅（主）** | **事件驱动**：成功满足一名顾客→结算「每单奖励」；半自动（有在岗员工即自动完成）+ 点「加把劲」拿 `ACTIVE_BONUS` | `I_eff`（复用 §3.1 全部旋钮，零重新调参） | **≈75–85%** | ❌ 无（需在线服务） |
| **B. 宿舍/撸毛馆（辅）** | **时间流**：恒定速率涓流（在线+离线），离线走「待领取上限+领取」 | `dorm_rate = DORM_SHARE × I_eff` | **≈15–25%** | ✅ 仅宿舍：`dorm_rate × OFFLINE_FACTOR(0.20)`，受 cap |

### 2.5.1 餐厅流（主，事件驱动）
- 复用 §3.1 的 `I_eff` 公式与全部旋钮（`Y_base / C / recipe / station / 三岗 / affinity / bond`）；结算方式由「连续每秒 accrual」改为「**离散每单结算**」：
  - `reward_per_order = I_eff × T_ORDER`（每完成一名顾客服务结算一笔，UI 飘字 `+reward_per_order★`）。
  - `T_ORDER`（秒/单，tunable，默认 **5s**，用户 2026-07-29 拍板由 3s 放慢）= 顾客服务周期；餐厅吞吐随座位/三岗提升而更快（`C_eff↑`→并发↑，`waiter/host` 缩短周期），**等效收入速率恒等于 `I_eff`**。
  - **半自动**：需求已解锁且有在岗员工→自动完成并结算；玩家点「加把劲」→ `active_bonus += ACTIVE_BONUS(0.15)` 增量（仅做增量，不削弱被动，见 §3.4）。
- 占比：餐厅流 = `I_eff`，占在线总收益 `I_eff / (I_eff + dorm_rate) = 1 / (1 + DORM_SHARE)`。

### 2.5.2 宿舍流（辅，时间流）
- `dorm_rate = DORM_SHARE × I_eff`；`DORM_SHARE`（tunable，默认 **0.25**）→ 宿舍占在线 **20%**、餐厅 **80%**（典型游玩）。
- 在线：场景无关涓流（切到市场/中枢仍累积），直接入账本（不经 pending）。
- 离线：**仅宿舍** accrual = `dorm_rate × OFFLINE_FACTOR(0.20)`，进 pending 缓冲、受 `capStars()` 限制（沿用 Phase 3.5 机制）；**餐厅无离线收益**。
  - `capStars() = dorm_rate × OFFLINE_FACTOR × OFFLINE_CAP_HOURS × 3600`（修订：base 由 `I_eff` 改为 `dorm_rate`，使离线封顶与「宿舍为辅」一致；`DORM_SHARE` / `OFFLINE_CAP_HOURS` 可调以放宽离线手感）。
- **食材**：仍仅宿舍时间流副产 `food_rate = 0.02 食材/秒`（在线，离线不计），严守红线「食材仅 idle 副产」。餐厅 serve 主产星券、不产食材。

### 2.5.3 新增 tunable（非锁参，待 engineering-lead 接入；标注待复核）
| 键 | 含义 | 默认 | 备注 |
|---|---|---|---|
| `DORM_SHARE` | 宿舍速率占 `I_eff` 比例 | 0.25 | 控制双流占比；↑→宿舍更肥、离线更可观 |
| `T_ORDER` | 餐厅每单服务周期（秒） | 5 | 控制离散结算节奏与飘字频率；不影响总速率 `I_eff` |

> 锁参不动：`OFFLINE_FACTOR=0.20` / `T_CAP_INIT=14400` 仅引用；抽卡锁参（`R60/SR30/SSR10` 等）与本次无关。

## 3. 数值设计

### 3.1 餐厅流 · 在线收益公式（星券/秒，事件驱动结算见 §2.5.1）

> 本节 `I_eff` 即**餐厅主收入流**的有效速率（§2.5）。公式与旋钮保持不变；结算改离散每单（§2.5.1），等效速率仍为 `I_eff`。

```
I_eff = C_eff × Y_base × recipe_mult × station_mult × chef_mult × waiter_mult × bond_idle_mult × ad_mult × (1 + active_bonus)
C_eff = C × host_mult
```

| 变量 | 含义 | 值 |
|---|---|---|
| `Y_base` | 基准单位座位产出 | 0.04 星券/秒/座（平衡可调） |
| `C` | 座位容量 | 初始 4，上限 24 |
| `C_eff` | 有效并发（接待岗加成后） | `C × host_mult` |
| `recipe_mult` | 菜谱倍率（菜谱升级树） | `1 + 0.10 × (recipe_lv − 1)` |
| `station_mult` | 工位倍率（工位升级树） | `1 + 0.10 × (station_lv − 1)` |
| `chef_mult` | 厨师岗总加成 = Π_i chef_mult_i（多员工**乘区叠加**，见 §3.3）；单只 `chef_mult_i = 1 + 0.08 × (chef_lv_i − 1)`，主适配岗再 ×affinity_bonus（默认 1.5，tunable） | （复核修正：原 `1 + 0.08×(lv−1)×affinity` 与 §3.3「适配独立乘区」表述冲突，已归一） |
| `waiter_mult` | 服务员岗总加成 = Π_i waiter_mult_i（乘区叠加，见 §3.3）；单只 `waiter_mult_i = 1 + 0.08 × (waiter_lv_i − 1)`，主适配岗再 ×affinity_bonus（默认 1.5，tunable） | （复核修正：原 `1 + 0.08×(lv−1)×affinity` 与 §3.3 冲突，已归一） |
| `host_mult` | 接待岗总加成 = Π_i host_mult_i（乘区叠加，见 §3.3）；单只 `host_mult_i = 1 + 0.06 × (host_lv_i − 1)`，主适配岗再 ×affinity_bonus（默认 1.5，tunable） | （复核修正：补「主适配岗 ×affinity_bonus」，与 §3.3 全岗适配规则一致） |
| `bond_idle_mult` | 羁绊 idle 倍率 | `1 + Σ(上岗且家人级动物 +3%)`，全局上限 +30%（见养成 GDD §3.2） |
| `ad_mult` | 加速广告 | 1（在线）/ 2（看「加速」广告）/ 离线见 §3.2 |
| `active_bonus` | 玩家主动加成（见 §3.4） | 被动基础结算之外的玩家派遣/点击增量，tunable |

> 顾客需求未解锁时该顾客不进入结算（占位不产出），故实际 `I_eff` 仅对「已解锁菜需求」的在岗顾客生效。

### 3.2 宿舍流 · 离线收益公式（离线仅来自宿舍，见 §2.5.2）

> 修订：离线 base 由 `I_eff` 改为 `dorm_rate`（§2.5.2）；餐厅无离线收益。

```
T_cap      = 离线累积上限（初始 4h = 14400s，可经装饰/钻石扩展至 12h）
offline_factor = 0.20（离线效率为在线 20%；平衡 pass v0.2 由 0.25 下调，放缓早期保底速度）
I_off     = I_eff × offline_factor
accumulated = I_off × min(T_off, T_cap)
```

- 离线为纯放置累积（无顾客交互），仅按 `I_eff` 被动 accrual。
- **回归奖励**：看「双倍产出」广告 → 当日首次领取 ×2；或「速回」用钻石立即结算。
- 超出 `T_cap` 部分不累积（软上限，防通胀）。

### 3.3 三岗加成（员工上岗，tunable）

- 每岗可排班员工数受**编制上限**约束（初始每岗 2，随座位/餐厅等级扩展，上限 8，tunable）。
- 单只员工在某岗的加成：
  - `chef_mult_i = 1 + 0.08 × (chef_lv_i − 1)`
  - `waiter_mult_i = 1 + 0.08 × (waiter_lv_i − 1)`
  - `host_mult_i = 1 + 0.06 × (host_lv_i − 1)`
  - 多只同岗按乘区叠加（不简单相加，防单岗堆叠失控）。
- **岗位适配（affinity）**：动物在**主适配岗**上岗时，该岗 mult 额外 ×`affinity_bonus`（默认 1.5，tunable）；非适配岗 ×1.0。适配判定来自程序化拼装参数 `role_affinity`（家族/属性决定）。
- **升级树 vs 岗位加成关系**：升级树（工位/菜谱每级 +10%）仍是 idle **主缩放量**；岗位加成（每级 +6~8%）为同量级软补充，不反超升级树；适配加成提供策略纵深但不改变锁参结构。

### 3.4 服务机制 = 被动基础 + 主动加成

- **被动基础结算**：顾客就座且菜已解锁后，在岗员工按 §3.1 公式自动结算，无需玩家操作（治愈「被照顾」内核）。
- **主动加成（active_bonus）**：玩家可主动介入拿额外收益，tunable：
  - **点击「加把劲」**：对当前在服顾客临时 `active_bonus += 0.15`（默认，持续 5s，可叠加次数设上限）。
  - **派遣匹配**：将「主适配岗」员工临时调往忙碌岗位，该顾客结算获得该岗 `affinity_bonus` 加成。
  - 主动加成只做**增量**，不削弱被动基础，保持零压力定位。

### 3.5 菜品解锁（新增 sink，星券 + 食材）

- 解锁成本（按解锁顺序索引 `n`，0-based，tunable）：
  - `unlock_cost_star(n) = 200 × 1.35^n`
  - `unlock_cost_food(n) = 40 × 1.30^n`
- **原子扣费**：星券与食材在同一服务端事务中同时扣减，任一方不足则解锁失败、不部分扣费（防作弊/防中途状态）。
- 解锁后该菜进入 `unlocked_dishes`，方可被顾客点单、进入结算。
- 初始默认可服务 1–2 道基础菜（出生时即解锁），保证新手期核心循环可跑通；其余菜经解锁逐步开放。

### 3.6 食材（次级资源）

- 厨房工位额外产出食材：`food_rate = 0.02 食材/秒`（基准），供养成喂食 **与** 菜品解锁双重消耗（闭环，不引入新资源）。

### 3.7 长线 sink（reset-less）

- **无转生 / 重置**；长线消耗：高阶升级（指数成本）、装饰/装扮、图鉴完成、限定收集、动物升星（碎片）、**菜品解锁（星券+食材）**。
- 数值通胀管控：星券产出增速（线性 × 分支） < 升级成本增速（指数 1.4–1.5×），迫使持续投入但不崩盘；食材因新增解锁 sink 多一条消耗通道，缓解副产堆积。

## 4. 边界与异常

- **离线超长**：`T_off` 仅按服务端时间戳计算，封顶 `T_cap`；改本地时钟无效（服务端校时）。
- **弱网 / 断线**：收益在服务端按时间戳结算，重连即领，无丢失。
- **容量边界**：`C` 达上限后升级座位按钮置灰；工位/菜谱等级上限锁；三岗编制满则提示扩编。
- **顾客需求未解锁**：顾客占座等待、不产出、无惩罚；UI 提示解锁对应菜。绝不扣血/扣资源。
- **菜品解锁中途**：原子扣费，星券或食材任一方不足 → 解锁失败、无部分扣除。
- **加速广告**：同一时段不叠加；看广告期间 `ad_mult=2`，结束回 1。
- **零动物**：新手 5 只 N 动物自动上岗（基础员工），经营不空转。
- **回归保护**：超过 7 日未登录，回归礼包 + 离线收益照常（治愈向不惩罚）。

## 5. 反作弊与安全

- **收益服务端权威**：在线/离线星券与食材以服务端按时间戳结算，客户端不可改。
- **菜品解锁原子性**：星券+食材扣减为服务端单事务，防本地篡改导致「只扣一种资源」。
- **防时钟回拨**：离线时长 = 服务端 `now − 上次心跳`，本地时间不参与。
- **广告防刷**：广告奖励由广告 SDK 回调服务端发放，客户端伪造回调无效。
- **产出速率护栏**：服务端校验单位时间产出不超理论上限（防加速器）。

## 6. 可访问性

- 文字 ≥18px；数字 Num 24–28px；暖墨 8:1 对比（art-bible §3.2）。
- 动效一键减弱：呼吸/粒子可关（reduce motion），保留静态定帧。
- 色盲安全：收益/状态/岗位不依赖颜色单编码（同 art-bible §9）；岗位用图标+文字双编码（厨帽/托盘/迎宾牌）。
- 触达：核心按钮 ≥44×44；座位/工位/顾客可点击区放大。
- 无声友好：收益有视觉「+」飘字，不依赖音效理解。

## 7. 依赖与接口

- **依赖**：账号/存档；经济（星券/食材余额）；养成（员工 `bond_idle_mult`、动物等级/适配岗影响各岗 `mult` 与 `T_serve`）；抽卡（提供动物 id/员工候选供上岗）；图鉴。
- **提供事件**：
