## 1. 版本号策略（SemVer）

采用 **语义化版本 `MAJOR.MINOR.PATCH`**（如 `v1.0.0`），并叠加微信小游戏特有的**提审/灰度通道**概念。

### 1.1 版本语义

| 位 | 含义 | 本项目示例 |
|---|---|---|
| `MAJOR` | 不兼容的玩法/内容大版本（含新增家族、新货币、锁参变更需走红线重审） | `v1` = 首发可玩 v1.0 |
| `MINOR` | 向后兼容的功能/内容增量（新增动物家族参数、季节活动、新场景分包、Live Ops 周期） | `v1.1` = 首个季节活动 + 图鉴分包 |
| `PATCH` | 向后兼容的修复/校准（热修、tunable 微调、文案修正、性能兜底） | `v1.0.1` = 首发热修 |

### 1.2 发布通道（与微信提审/灰度对应）

| 通道 | 版本后缀 | 用途 | 受众 |
|---|---|---|---|
| `alpha` | `v1.0.0-alpha.N` | 内部开发自测、真机证伪（V4–V7 / R1–R7） | 团队 + 真机 |
| `beta` | `v1.0.0-beta.N` | 封闭 Playtest / 招募玩家小样本校准（见 `v1-calibration.md`） | 受邀请玩家 |
| `rc` | `v1.0.0-rc.N` | 提审候选 + 全量灰度前最终回归 | 全量灰度前 |
| `stable` | `v1.0.0` | 正式上线 | 全量 |

> 微信小游戏本身无"channel"字段，通道靠**体验版（开发版/体验版）+ 提审版 + 线上版**三态实现：`alpha/beta` → 开发版/体验版；`rc` → 提审版；`stable` → 线上版。`game.json` 的 `version` 字段（及 `project.config.json` 同步）须与发布通道对齐。

### 1.3 锁参红线版本冻结规则

- **锁参红线（`src/config/tunables.js` 的 `LOCKED`：`offline_factor=0.20`、`T_CAP_INIT=14400`、稀有度 N/R/SR/SSR、R池 60-30-10、50 保底、四货币定义）在 v1.0 全周期内视为冻结**。任何改动须经"用户显式授权 + design+eng 双签 + 重跑 `balance-sim.js` + 回归基线"方可，且需 bump `MINOR` 或 `MAJOR`（红线变更即非纯修复）。
- **TUNED 段 tunable（DORM_SHARE / T_ORDER / 解锁曲线 / 三岗加成 / 升级成本等）可在 `PATCH/MINOR` 内校准**，但须走 §9 门控 + `v1-calibration.md` 双签流程，且每次变更留 `changelog`（见 §4）。

### 2.3 合规要点（发布前必检）

- **概率公示（关键）**：抽卡概率 **R60% / SR30% / SSR10%**、**50 抽硬保底**、软保底阶梯、十连 ≥1SR、新手前 10 抽 ≥1SR 必须在**游戏内可查阅处公示**（如"概率说明"入口），与 `LOCKED` 口径逐字一致。`art-bible.md §7.2` 双编码 + 折叠小字合规（见 HANDOFF §7-D 保底展示粒度/概率公示样式待确认）。
- **IAP 合规**：虚拟支付走微信官方支付；`game.js` 动才市场"换钻/礼包"当前为 `wx.showModal` 占位（`DEV_IAP_GRANT` 保护），真实支付形态待用户定（HANDOFF §7-E / QA R4）。
- **广告合规（IAA）**：广告位权重"次级可选"（HANDOFF §7-E）；须接入微信广告组件并合规展示。
- **内容合规**：治愈向、零失败无惩罚、无违规；角色/文案不触碰平台敏感词。
- **数据合规**：用户数据本地存储（`storage.js` 三级：wx→localStorage→内存），不越权上传；远程资源域名白名单须在微信后台配置（`art-bible.md §A.5`）。

## 3. 构建与分包策略（衔接已知待办 R2）

### 3.1 现状（已核查）

- `game.json` **当前无 `subpackages` 字段**（QA R2 已确认）；`project.config.json` 亦无分包配置。
- 主包体积：`build-size.gate.js` 报告 **132334 B ≈ 129.23 KB**（engineering-lead 复核），sprint-5 自报 84.80KB（口径差异见 QA R1，**以 `build-size.gate.js` 为权威门**）。**远小于 4MB 硬限**，当前零贴图 + 程序化图元方案使 atlas 字节恒=0（不变量 #1）。
- 单只动物 = 0 独立贴图、~11–64B 参数；**动物数量增长几乎不挤压主包**（art-bible §A.4）。

### 3.2 分包引入时机（判定阈值）

**当前不建议引入分包**——主包仅 ~131KB，远低于 4MB，强行分包只增构建复杂度。引入分包的触发条件（任一满足即启动）：

| 触发条件 | 阈值 | 说明 |
|---|---|---|
| 主包逼近 | ≥ **3.0 MB**（留 1MB 缓冲） | 真机证伪后按实测包体定 |
| 非核心内容增量 | 新增"完整场景/扩展图鉴/音频音乐/季节活动"任一 | 这些本就是 HANDOFF §2 规划的分包候选 |
| 真机证伪 V7 | 分包命中须真实构建 + 微信真机证伪（最大未消项） | 未证伪前分包标 N/A 不阻塞 |

### 3.3 分包预算与拆分（规划，待真机校准）

| 分包 | 内容 | 预算（建议上限） | 加载时机 |
|---|---|---|---|
| `sub-restaurant` | 餐厅完整场景（迎宾/就餐/后厨精细化 + 后续区域） | ≤ 1.5 MB | 首次进入餐厅 |
| `sub-roster` | 扩展图鉴（首发 36→长线 60–80 参数组） | ≤ 1 MB（参数极小，实际远低） | 首次进入图鉴 |
| `sub-audio` | 音乐 + 音效（audio-director 接入后） | ≤ 2 MB（天花板；实际默认几乎不占，见脚注②） | 首次进入需音频的场景 / 设置开启 |
| `sub-event` | 季节/活动运营资源（限定动物参数、活动 UI） | 按需，≤ 1 MB/活动 | 活动开启时 |

> ① **分包门控**：V7 证伪 R2 为发布前必检，未证伪须显式记录为 N/A（见 §2.4 QA 项）。
> ② **音频分包脚注（与 audio-director §3.3 对齐，2026-07-30 协同）**：默认 100% 程序化合成路径**无远程音频 → 无需微信后台域名白名单**；仅当改为「(b) 远程流式采样」时才需白名单，由启用方提前就绪。audio-director 建议：**程序化核心（BGM 三套层 + 22 条 SFX）作为 v1.0 候选接入**——零字节、零包体风险、兑现 concept §2.3「Sensation 软萌音效」支柱，且为 v1.0 **非阻塞项**；**(b) 采样增强（若有）放 v1.1**，默认 0 字节、实际支出控 ≤512KB（远低于本表 2MB 天花板），**无需拆「音乐/音效」两个分包**——保持单 `sub-audio` 即可。v1.0 程序化核心是否首发为**发布门控/主理人裁定项**（非 audio-director 擅设）。

> 首包（≤4MB）始终只放"能玩的最小集"：核心 UI 骨架 + canvas2d 绘制库 + 字体子集 + 程序化背景参数 + 首只动物参数 + 抽卡演出 VFX（art-bible §A.4）。**分包门控：V7 证伪 R2 为发布前必检，未证伪须显式记录为 N/A（见 §2.4 QA 项）**。

### 3.4 构建产物与体积门

- 体积门：`node tests/smoke/build-size.gate.js` 退出码 0（<4MB）为发布硬门（QA §1.2）。
- `packOptions.ignore`（已配置）：`node_modules / tests / production / design / docs / art / jest.config.js / src/analysis / HANDOFF.md / §5-revision-report.md / .workbuddy / src/prototype / .github / package.json / project.private.config.json` 均不进发布包——确保文档/测试不占包体。
- 发布包应仅含：运行时 `src/`、`game.js`、`game.json`、`project.config.json`、字体子集、必要配置。**任何新增文档/资源必须走 ignore 或分包**，不得误入主包。

## 5. 本地化（Localization）

### 5.1 首发范围建议

| 维度 | 建议 | 理由 |
|---|---|---|
| 首发语言 | **简体中文（CN）优先** | 女性向治愈受众主阵地；零贴图 + 程序化文案使本地化成本集中于字符串表而非资产 |
| 首发地区 | 中国大陆（微信生态） | 平台硬约束为微信小游戏，首发聚焦大陆 |
| 后续扩展 | 繁中 / 英 / 日（标记"后续"，见 §5.3） | 治愈向在东亚（日/港台）有受众，但需先验证 CN 留存 |

### 5.2 文案风格指南（与 art-bible 情绪一致）

核心情绪锚点（art-bible §1）："被陪伴的安心感"——马卡龙/奶油低饱、圆润幼态、温暖松弛无攻击性。

| 维度 | 规范 | 反例（规避） |
|---|---|---|
| 语气 | 暖、轻、陪伴感；第二人称"你"+"小动物"拟人 | 冷硬指令式"请完成订单" |
| 用词 | 软词：来呀 / 坐会儿 / 加把劲 / 慢慢来 / 陪你 | 硬词：必须 / 强制 / 失败 / 惩罚 |
| 标点 | 适度语气词与emoji化留白（非强制）；多用"～""呀" | 过多感叹号/全角标点堆叠 |
| 数值沟通 | 收益用"飘字 +N★"正向反馈；不展示"亏损/惩罚" | 不出现负向数值恐吓 |
| 稀有度演出 | SSR 用全屏彩带/星屑（art-bible §8.3），文案配"恭喜遇见" | 不渲染"欧非/焦虑" |
| 一致 | 与 art-bible §6 字体/UI 语气（圆体、暖墨）协同；可达性：正文≥18px、暖墨 8:1 | 不破坏色盲双编码（§7.2/§9） |

### 5.3 多语言扩展路线（标记"后续"）

1. **字符串表抽取**：扫描 `src/` 硬编码中文字符串（Grep `[\x{4e00}-\x{9fff}]` + 模板字面量），抽取到 `src/i18n/strings.{zh,zh-TW,en,ja}.json`（**当前未建，列入 v1.1+ 规划**）。
2. **译员简报**：基于 §5.2 风格指南 + art-bible 情绪，给译员"暖/轻/陪伴"基调简报 + 禁止项清单。
3. **文化/敏感性评审**：地区禁忌（动物象征、节日、颜色）逐语言评审。
4. **字符串冻结**：v1.0 锁参冻结同期，文案在提审前冻结；热修外禁改字符串（避免破坏已译内容）。
5. **RTL/平台**：本项目为 LTR 中文优先，RTL 不在 v1.0 范围；若扩阿拉伯语再评估。

> 本地化不触碰任何 tunable / 锁参；仅影响字符串表与补丁说明语言。

## 6. Live Ops（活动节奏 / 内容日历 / 留存）

### 6.1 设计约束（与双流经济对齐）

- 所有 Live Ops 须**不破坏锁参红线**：不得引入新货币、不得改 R池/保底/四货币定义、不得动 `offline_factor`/`T_CAP`。
- 活动奖励须经"星券/钻石/食材/碎片"四货币之一结算，且**食材仅限在线 idle 副产逻辑**（不得让活动产食材破坏离线不计食材红线）。
- 活动节奏须与 `v1-calibration.md` 校准结论协同，避免活动叠加导致后期 flooding（phase2-balance §2 发现 2）失控。

### 6.2 活动节奏骨架（周期 / 季节）

| 类型 | 周期 | 内容骨架 | 目的 |
|---|---|---|---|

### 7.1 危机沟通原则

- 概率/保底相关质疑：以游戏内公示 + `LOCKED` 口径为准，透明回应，不删帖不回避。
- 热修/回滚：通过公告（补丁说明，§4.2 风格）主动告知玩家"我们调顺了什么、何时生效"，降低不安。

## 8. 回滚策略（构建回退 / 热修流程）

### 8.1 构建回退（版本级）

- 微信小游戏支持**回退到上一线上版本**（平台能力）；每次发布留"上一稳定版"构建产物 + 对应 `changelog` + tunables 快照。
- **回退触发**：PATCH 发布后核心指标（崩坏率/留存）显著劣化、或锁参红线被误触（紧急）。
- **回退不丢数据**：玩家存档在 `storage.js` 三级（wx→localStorage→内存），版本回退不应破坏存档前向兼容；tunable 回退须保证存档字段兼容（如新增 tunable 旧版缺省处理）。

### 8.2 热修流程（Hotfix，简化但保留审计+回滚）

- **适用**：纯逻辑修复、tunable 微调（仅 TUNED）、文案修正、性能兜底。**禁止**：锁参红线改动、新货币、架构变更。
- **流程**：
  1. 提 issue（qa-lead `bugs/`）→ 2. 修复（仅 scope 内文件）→ 3. `npm test` 159/159 + `build-size.gate.js` <4MB + `node game.js` boot OK → 4. **锁参红线自检**（grep `LOCKED` 零改动）→ 5. 主理人/用户审批 → 6. 提审/体验版验证 → 7. 灰度 → 8. 全量 + 留上一版快照。
- **审计**：每次热修留 `changelog`（§4.1）+ tunables diff + 审批记录；保留回滚预案（§8.1）。
- **灰度**：微信体验版→小比例线上灰度→全量；灰度期监控崩坏/留存。

### 8.3 事故分级与响应

| 级 | 定义 | 响应 |
|---|---|---|
| P0 | 锁参红线误触 / 大规模崩坏 / 数据丢失风险 | 立即回滚（§8.1）+ 主理人+用户通报 |
| P1 | 核心循环受阻（如离线领取失效）/ 付费异常 | 热修（§8.2）或回滚，24h 内 |
| P2 | 非核心体验问题（如某活动 UI 错位） | 排期热修，不阻塞 |

## 9. 发布门控（Go / No-Go）

### 9.1 跨部门 Checklist（与 §2.4 同源，汇总为 go/no-go）

| 域 | 负责人 | GO 条件 | Blocker? |
|---|---|---|---|
| 工程 | 程基岩 | 三门禁全绿、锁参零改动、DEV_DEMO_SEED=false | 是 |
| 设计 | 文策渊 | §5 校准闭环、锁参未动、概率文案对齐 | 是 |
| 美术 | G | art-bible/asset-spec/system-scene-phase2 签字（**当前未签 🔴**） | 是（关键） |
| 音频 | H | 方向接入（当前未启动 ⚪） | 否（可后置到 v1.1） |
| QA | 严守真 | 烟雾 S1–S12 全 PASS、真机 §4 勾选、R1–R5 显式记录 | 是（冒烟 FAIL 即阻断） |
| 法务/资质 | 用户 | L1–L5 闭合、隐私指引、版号状态明确 | 是（上线窗口） |
| 运营/社区 | 路远行 | 公告/概率页/客服/回滚预案就绪 | 否 |
| 分包 | 程基岩 | V7 证伪或显式 N/A 记录（R2） | 否（N/A 不阻塞） |

### 9.2 判定规则

- **GO**：无 Blocker 未消，或用户显式豁免某 Blocker（须书面记录豁免原因）。
- **NO-GO**：任一 Blocker 未消且未获豁免 → 不发布。
- **Blocker 示例**：锁参红线被改、`npm test` 非全绿、主包 ≥4MB、美术签字缺失（G）、版号/资质未明、冒烟 FAIL。
- **审批**：最终放行由**主理人（游承峰）/用户**人工决定；release-ops-lead 只给门控判定与清单，不自行发布。
