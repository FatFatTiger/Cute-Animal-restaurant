## 0. 已锁定决策（不可重开，本文件全部内容受其约束）

| 项 | 决策 |
|----|------|
| 平台 | 微信小游戏（微信客户端运行时 + 引擎插件，运行时不计入 4MB 主包） |
| 引擎 | Cocos Creator + 微信引擎插件（ADR-1） |
| 资产策略 | 程序化拼装：单张白模 base-parts atlas + JSON 参数；单只动物 ~11B（ADR-2） |
| 家族硬隔离 | 跨家族部件组合运行时拒绝，抛 `FamilyIsolationError`（ADR-2 / R-GUARD-NUANCE 白名单例外保留） |
| 分层上色 | 身份色（角色层）vs 稀有度色（UI 卡框层）分属不同 UI 层，Shader tint（ADR-4） |
| 稀有度 | N / R / SR / SSR；抽卡池 R60% / SR30% / SSR10%，N 不入池；50 抽硬保底 |
| 货币 | 星券（免费，放置产出）/ 钻石（付费，IAP）/ 食材（经营副产）/ 碎片（抽卡重复） |
| 分包 | 餐厅场景 / 扩展图鉴 / 音频音乐 / 活动运营（ADR-3） |
| 主包预算 | 硬上限 4MB；首屏实测目标 ≈1.3–1.9MB（tech-prototype §4） |

> 真机/构建待证伪项（V4–V7、R1–R7）在预生产阶段**不实现**，仅在 Epic 依赖与验收中标记「待证伪」，在测试框架（tests/README.md）中留烟雾/CI 门禁占位。

## 2. Epic 详述

### E1 · 核心框架与运行时（L1 + L2）
- **目标**：搭建微信小游戏运行容器、生命周期、引擎插件注入、分包加载器、L2 服务封装（渲染/输入/本地存档/网络登录/分享），为所有上层系统提供零依赖基座。
- **范围边界（In）**：引擎插件加载与版本校验；首屏引导白模 atlas 与引导 JSON 加载；通用存档封装；分包按需下载/缓存/解压调度；全局错误边界与降级。
- **范围边界（Out）**：任何具体玩法逻辑（归 E2–E6）；真实微信支付/广告 SDK（归 E8）；真机性能调优（归 R1/R7，仅留探针接口）。
- **依赖**：微信引擎插件（外部，R2/R6 待证伪）；无内部前置依赖，是其他所有 Epic 的地基。
- **验收标准**：
  - [ ] 引擎插件注入成功，首屏冷启动进入可交互状态（V6 待真机证伪，CI 留门禁）。
  - [ ] 主包体积 < 4MB（V4，阈值由 tests/README.md §4 CI 门禁保障）。
  - [ ] 分包按 ADR-3 清单（餐厅场景/扩展图鉴/音频音乐/活动运营）按需命中，未命中时 Loading 不卡死（V7 待构建证伪）。
  - [ ] 本地存档封装通过 `wx.getStorage`/`setStorage` 异步与同步双路径单测（不依赖真机）。
  - [ ] 引擎插件版本与构建版本一致性校验失败时有可观测告警（R2 探针）。

### E2 · 程序化拼装管线（L3）
- **目标**：将 `assembly-demo.js` 的已验证逻辑层（atlas 槽位映射 / 家族硬隔离 / 分层 tint / 紧凑打包）工程化为 Cocos 可用的生产模块，并保证「加动物 = 零贴图字节增长」。
- **范围边界（In）**：base-parts atlas 管理（引导子集进主包、完整集进扩展图鉴分包）；`slotAllowed`/`validateFamily`/`FamilyIsolationError`；`assembleCharacter`（z-order body→head→ear/tail→face→accessory，分层 tint 入口）；`packAnimal`/`unpackAnimal`（≤64B/只，打包前钳制防回绕，R-ENCODE）；`COLOR_PRESETS` 12 套；`RARITY` 双编码。
- **范围边界（Out）**：WebGL 着色器具体实现（R3 待真机证伪，本 Epic 仅定义 tint 入参与分层契约）；实际美术生产（美术资产，交林绘澄）；动物数值/稀有度定义（归图鉴/抽卡 GDD）。
- **依赖**：E1（运行时与分包加载）；`assembly-demo.js`（逻辑基线）；美术提供的 atlas 烘焙产物（R-ATLAS-CONST：绝对基线须以真实烘焙图集替换 `ATLAS_BYTES`）。
- **验收标准**：
  - [ ] atlas 字节零增长断言：新增 N 只动物 `delta = 0`（V1，单测 + CI 门禁）。
  - [ ] 单只参数 `≤ 64B`（V2）。
  - [ ] 跨家族组合运行时抛 `FamilyIsolationError`；`universal` 与显式多家族槽位（L0=[mammal,bird]、L2=[round,aquatic]）白名单通过（V3，R-GUARD-NUANCE）。
  - [ ] `packAnimal` 对 `deform` 在打包前钳制/校验，超界不静默回绕（R-ENCODE）。
  - [ ] 分层 tint 契约（身份色 vs 稀有度色分 UI 层）与 ADR-4 一致，真机还原留 R3 门禁。

### E3 · 抽卡系统（L4）
- **目标**：实现单常驻池的稀有度摇号、保底计数、重复转碎片、升星与溢出回收，以及服务端权威的事务边界（本预生产阶段先落*可单测的纯逻辑核心*，服务端接入归 R5/R6 待证伪）。
- **范围边界（In）**：概率表 R60/SR30/SSR10（N=0%）；`pity ∈ [0,50]` 全局计数（跨货币共享、SSR 归零）；硬保底 `pity≥50→SSR`；软保底 `c∈[41,49]` 阶梯 `SSR_rate(c)=min(1,0.10+0.09×(c−40))`；十连 9 折且保底 ≥1 SR；新手前 10 抽 ≥1 SR；重复转碎片 R20/SR50/SSR100；升星阈值 R80/SR150/SSR300；满星溢出回收 `1碎片={R2/SR5/SSR10}星券`；`requestId` 幂等去重；`onGachaResult` 事件。
- **范围边界（Out）**：真实微信计费链路（归 E8/R6）；抽卡演出特效（归 E7/E9，仅预留 `onGachaResult` 订阅）；真实服务端（预生产以「可注入的权威实现」抽象，便于单测，真机接入后续 Sprint）。
- **依赖**：E6（星券/钻石/碎片单值源）；E5（升星→碎片→等级上限）；图鉴动物定义（id/稀有度）；E2（卡面程序化拼装入口）。
- **验收标准**：见 system-gacha.md §8 全部 8 条；并补：概率分布蒙特卡洛单测（大样本 R≈60%/SR≈30%/SSR≈10%）；保底计数在单抽/十连/每日免费抽均 +1；货币不足/弱网/断线重连不扣费（服务端权威抽象）。

### E4 · 放置经营（餐厅）· 顾客带需求上门模型（L4）
- **目标**：实现 `顾客上门(带菜需求) → 员工三岗服务 → 结算(星券/食材) → 解锁菜品/升级扩张` 核心循环，作为星券唯一生产源；含在线/离线收益、升级树、员工三岗排班与岗位加成、顾客需求匹配、食材副产。
- **范围边界（In）**【模型已按 GDD v0.2 修订，旧「visitor」模型废弃】：
  - 顾客上门携带「想吃的菜」需求；**该菜未解锁则无法服务**（占位不产出、无惩罚），解锁成核心驱动（联动 E11/E12）。
  - 在线收益 `I_eff = C_eff × Y_base × recipe_mult × station_mult × chef_mult × waiter_mult × bond_idle_mult × ad_mult × (1 + active_bonus)`，其中 `C_eff = C × host_mult`；三岗加成 `chef/waiter +8%/级`、`host +6%/级`、适配 `affinity_bonus=1.5`、主动 `active_bonus=+0.15`（**以上均引用 GDD system-idle-restaurant v0.2，标 tunable，待 design-strategist 复核签字，非锁参**）。三岗 mult 按 GDD §3.1↔§3.3 归一口径：单岗乘区叠加 + 适配独立乘区，旧内嵌 `×(lv−1)×affinity` 写法已废弃（详见 E4-S2 / §3.3）。
  - 离线收益 `accumulated = I_eff × 0.20 × min(T_off, T_cap)`（`offline_factor=0.20` 为**锁参红线**，T_cap 初始 14400s 可扩至 12h）。
  - 升级成本 `seats 200×1.5^n`、`stations/recipes 150×1.4^n`；员工三岗排班（厨师/服务员/接待，含岗位适配 `affinity`）；服务 = 被动基础结算 + 玩家主动派遣/点击加成；食材 `0.02/s`；5 只 N 动物自动上岗；`onEarn` / `onCustomer` / `onDishUnlock` 事件。
- **范围边界（Out）**：餐厅场景美术与渲染（归美术 + 餐厅场景分包，本 Epic 仅逻辑）；真实广告 SDK 加速（归 E8，仅预留 `ad_mult` 入口与回调契约）；真实服务端时间戳（预生产以可注入时钟抽象，真机接入归 R4/R5）。
- **依赖**：E6（星券/食材单值源 + `requestId` 幂等）；E5（`bond_idle_mult`、`T_serve`、岗位适配 `role_affinity`）；E11（菜品解锁原子扣费与成本曲线）；E12（顾客生成与需求匹配）；E1（分包加载：餐厅场景分包）；抽卡（提供可上岗动物 id）。
- **验收标准**：见 system-idle-restaurant.md §8 全部 11 条；并补：离线 `T_cap` 封顶单测（超时不累积）；防时钟回拨（服务端时间戳抽象）；满座无死锁；升级上限按钮置灰；**需求未解锁顾客占位不产出、无惩罚**；**三岗加成与适配加成乘区正确**；**主动加成仅做增量不削弱被动**。

### E5 · 养成系统（L4）
- **目标**：实现喂食/送礼/装扮→好感/XP→羁绊阶层→里程碑加成，产出 idle 倍率 / 碎片加成 / 服务速度加成。
- **范围边界（In）**：好感 `A∈[0,100]`；羁绊 5 阶层（陌生0/熟悉20/朋友50/挚友80/家人100）；喂食 1 食材→+1 好感 +10 XP；送礼 +5 好感 +50 XP（每日 3 次）；`XP_need(lv)=100×lv^1.3`；等级上限 base20 +10/星（满星 5→70）；idle +3%/只（前 10 上岗计，上限 +30%）；碎片 +10%（上限 +20%）；挚友 `T_serve −5%`；升星提升等级/加成上限；`onBondChange` 事件。
- **范围边界（Out）**：养成美术/表情动画（归美术 + 扩展图鉴分包）；独立付费养成货币（明确禁止，见 system-cultivation §3.3）。
- **依赖**：E6（食材余额）；E3（动物 id/碎片/升星）；E4（食材来源、上岗工位、`I_eff`、`T_serve`）；E2（表情切换装配入口）。
- **验收标准**：见 system-cultivation.md §8 全部 8 条；并补：好感满 100 溢出转 XP；下岗加成实时增删无残留；升星碎片不足拦截；与经营/抽卡 GDD 数值完全一致（无矛盾）。

### E6 · 货币与经济（L4 / L5）
- **目标**：建立四货币（星券/钻石/食材/碎片）的**单值源账本**与守恒不变式，是所有经济流动的中央枢纽，杜绝双计。
- **范围边界（In）**：货币类型定义与余额账本；所有增减走统一事务接口（带 `requestId` 幂等）；星券为「放置经营 + 抽卡」同一货币（system-idle §7、system-gacha §2 一致）；钻石不进放置产出（防通胀，system-gacha §3.6）；碎片为抽卡重复产物的二级账本；守恒校验钩子（供集成测试，tests/README.md §3 不变量 3）。
- **范围边界（Out）**：具体产出公式（归 E3/E4/E5）；支付/广告发放（归 E8，仅预留「服务端回调写入余额」契约）。
- **依赖**：E1（存档封装，余额持久化）；E3/E4/E5（调用方）。
- **验收标准**：
  - [ ] 任意关闭交易批次内：`Σ产出 = Σ消耗 + Δ余额`（货币守恒单测，tests/README.md 不变量 3）。
  - [ ] 星券单值源，放置与抽卡共用同一余额，不双计。
  - [ ] 钻石不经由放置经营产出路径进入。
  - [ ] 幂等：同一 `requestId` 重复提交余额只变更一次。

### E7 · UX 外壳与导航（L5）
- **目标**：主菜单 / 图鉴 / 餐厅 / 抽卡 / 商店的导航壳与 UI 框架；cc.Node 树**不持有游戏状态**（状态归 L4/E6）；可访问性基线。
- **范围边界（In）**：页面路由与生命周期；底部导航 / 入口；抽卡概率公示固定入口（合规）；稀有度双编码（颜色+角标形状+纹理，色盲安全）；动效可减弱（reduce motion）；核心按钮 ≥44×44；文字 ≥18px、数字 24–28px。
- **范围边界（Out）**：具体玩法交互细节（归各玩法 Epic）；演出特效资源（归美术）。
- **依赖**：E1（运行时/分包）；E3/E4/E5/E6（数据与事件订阅，UI 只读不持状态）。
- **验收标准**：
  - [ ] 所有页面通过事件订阅渲染，组件内无游戏状态字段（控制清单：UI 不持有游戏状态）。
  - [ ] 可访问性：稀有度三重编码、动效可跳过、文字/热区达标（对齐三份 GDD §6）。

### E8 · 商业化（IAP + IAA）（L5）
- **目标**：微信支付（钻石礼包/月卡）与激励视频广告（加速/双倍产出）的接入抽象、幂等发放与防刷；活动运营分包承载运营配置。
- **范围边界（In）**：支付/广告 SDK 封装与回调→服务端→余额写入契约（R5/R6 待真机证伪，预生产只落「可注入的支付/广告权威实现」抽象 + 单测）；广告奖励由 SDK 回调服务端发放（防客户端伪造，system-idle §5）；活动运营分包加载与配置热更入口。
- **范围边界（Out）**：真实微信支付/广告联调（R5/R6 待证伪）；具体活动玩法（归后续 Epic）。
- **依赖**：E6（余额写入）；E4（加速/双倍广告入口）；E1（活动运营分包）；微信支付/广告 SDK（外部）。
- **验收标准**：
  - [ ] 支付/广告奖励仅经「SDK 回调 → 服务端 → 余额」链路发放，客户端伪造回调无效（抽象层单测）。
  - [ ] 活动运营分包按需命中（ADR-3）。
  - [ ] 真实链路待 R5/R6 真机证伪，CI 留 smoke 占位。

### E9 · 音频（L2 / L5）
- **目标**：BGM/SFX/语音的加载、播放、静音与「无声友好」降级；资源进音频音乐分包。
- **范围边界（In）**：音频音乐分包按需加载；全局静音/音量；收益/状态有视觉「+」飘字不依赖音效（system-idle §6 无声友好）；SSR 抽出轻柔 haptic（可关）。
- **范围边界（Out）**：具体音频资产（交美术/音频）；WebAudio/微信音频 API 真机表现（R3 相关）。
- **依赖**：E1（分包加载：音频音乐分包）；E7（UI 触发）；各玩法 Epic（事件触发音效）。
- **验收标准**：
  - [ ] 音频音乐分包按需命中（ADR-3）。
  - [ ] 静音状态下核心反馈（收益飘字/状态）仍完整可读。
  - [ ] 真机音频表现待 R3 证伪，CI 留 smoke 占位。

### E10 · 发布与分包（L1 / L3）
- **目标**：构建管线、分包切分、主包体积门禁（<4MB）、真机构建与分包下载验证，把「4MB 主包风险在架构层消解」从逻辑论证推到构造性证明。
- **范围边界（In）**：Cocos 构建（引擎外置）+ 微信分包配置（ADR-3 四分包）；主包体积测量与 `<4MB` 门禁（V4）；分包下载/解压耗时观测（R4）；首包预算表（tech-prototype §4）落地校验。
- **范围边界（Out）**：玩法内容（归各 Epic）；真机性能调优（R1/R7 仅观测）。
- **依赖**：E1–E9（产出需被正确切分进主包/分包）；微信开发者工具 / 真机构建环境。

  - [ ] 分包下载/解压耗时有观测埋点（R4）。

### E11 · 菜品研发与解锁经济（L4）
- **目标**：实现「菜品解锁」这一长线 sink：消耗星券 + 食材**原子扣费**解锁新菜，并记录菜谱解锁进度，使「解锁菜品」成为顾客服务与经营扩张的核心驱动（驱动 E12 顾客可服务性、E4 结算）。
- **范围边界（In）**：菜品解锁**原子扣费**（星券 + 食材同一事务同时扣减；任一方不足则两侧均不扣减，无悬挂账本）；菜谱解锁进度（`unlocked_dishes` 集合 + 初始默认 1–2 道基础菜，保证新手期核心循环可跑通）；解锁成本曲线 `unlock_cost_star(n) = 200 × 1.35^n`、`unlock_cost_food(n) = 40 × 1.30^n`（**以上成本公式引用 GDD system-idle-restaurant v0.2，标 tunable，待 design-strategist 复核签字，非锁参**）；解锁成功发 `onDishUnlock{dishId, costStar, costFood}`。
- **范围边界（Out）**：具体菜谱内容/美术（归策划/美术）；解锁后的顾客结算收益（归 E4/E12）。
- **依赖**：E6（星券/食材单值源 + `requestId` 幂等，复用不变量 3/6 语义）；E12（解锁后方可被点单）。
- **验收标准**：见 system-idle-restaurant.md §8「菜品解锁原子扣费」条；并补：原子扣费单测（成功路径两侧同扣、失败路径零扣减、幂等）；成本曲线按 n 单调递增、与 v0.2 公式一致（tunable 标注）；解锁进度持久化与幂等（同 `requestId` 只解锁一次）。

### E12 · 顾客系统（L4）
- **目标**：实现顾客生成、需求分配与「需求 ↔ 已解锁菜品」匹配，使未解锁需求的顾客无法被服务（占位不产出、无惩罚），从而把驱动压力导向 E11 菜品解锁。
- **范围边界（In）**：顾客按节奏到店（T_spawn）占座并携带一个 `dish_demand`；需求-已解锁菜品匹配（已解锁且有对应在岗员工 → 可服务、计入 `I_eff`；未解锁 → 不可服务、占位零产出、UI 提示解锁）；匹配结果可复现（seeded）。
- **范围边界（Out）**：顾客美术/动画（归美术 + 餐厅场景分包）；结算数值（归 E4）；需求菜品内容池（归策划 + E11 菜谱）。
- **依赖**：E4（三岗在岗员工判定、结算入口）；E11（已解锁菜品集合）；E6（结算星券/食材落账）。
- **验收标准**：见 system-idle-restaurant.md §8「需求未解锁顾客占位不产出」条；并补：未解锁需求不进入结算（不贡献 I_eff）单测；已解锁+在岗可服务并计入 I_eff；匹配在固定种子下可复现（不变量 7）。
